# Portfolio and template architecture audit

## Current baseline

The approved homepage is the portfolio design baseline. The React Router tree, shared layout, suite routes, and existing booking demonstrations carry forward. Phase 3 adds a site-wide fictional-property disclosure to local development and the review build. The homepage conversion is included in v0.3.0-preview. Metadata and booking-placeholder changes remain separate follow-up work.

## Reuse model

Start with one typed configuration object per project and the existing reusable components. Resolve the active profile at build or application startup. Keep the public demo deployment, storage, users, and credentials separate from any real-client project. Keep staging crawler controls where relevant. Choose a client's indexing and hosting policy for that client explicitly. Avoid tenant selection, shared reservation tables, and tenant-routing middleware until an actual product requirement exists.

## Safe learning boundaries

- **Availability:** Seed fake inventory. Use property-local dates and stable suite IDs. Treat the checkout date as an exclusive boundary when checking conflicts.
- **Reservations:** Persist only simulated requests. Keep customer PII out of the public demo. Use test fixtures, server validation, transactional conflict checks, repeat-submit protection, and a reset path.
- **Administration:** Start locally with fake operators and seeded records. Put authorization checks on the server, restrict writes to demo data, and prevent public admin sessions from reaching any client system.
- **Payments:** Default to a mock adapter that can simulate success, failure, refunds, and duplicated events. Keep any optional sandbox work separate, use only test credentials and synthetic payment data, and never expose a real checkout or accept real card information.
- **Communications:** Render fake confirmations onscreen or into a local test outbox. Avoid sending unsolicited email or SMS.
